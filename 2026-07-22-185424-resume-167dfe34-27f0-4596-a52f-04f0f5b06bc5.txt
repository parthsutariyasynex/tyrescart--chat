● Here's the key thing that clears this up: displaying the image never involves 
  a GraphQL call for the image file itself.

  GraphQL only returns a URL string (item.image.url, e.g.
  https://www.tyrescart.com/media/catalog/product/x/y/tyre.jpg). The actual
  image bytes are then loaded by the browser directly from the Magento media
  server via <Image src={...}> — that's a plain image request to /media/..., not
  a GraphQL request, and it has no CORS problem (image tags aren't subject to
  the fetch CORS block that broke the proxy removal).

  So GraphQL's only role for images is telling you where the image lives. To
  show an image with no GraphQL call at all, you'd need that URL from somewhere
  else. Your realistic options:

  1. Use the cache you already have (recommended).
  The app caches GraphQL responses in IndexedDB (services/cache.ts). After the
  first load, item.image.url is already stored, so repeat visits render images
  with zero GraphQL calls — the browser just fetches /media/... directly. This
  is essentially already how it works.

  2. Construct the media URL from SKU — usually not reliable.
  Magento stores images under a hash-based path
  (/media/catalog/product/a/b/<original-filename>). The filename is whatever was
  uploaded, not derivable from the SKU, so
  https://www.tyrescart.com/media/catalog/product/${sku}.jpg will 404 for most
  products unless your store happens to enforce a strict SKU-based naming
  convention. I wouldn't rely on this.

  3. Static/local placeholder.
  You already have an SVG fallback for missing images — that needs no network
  call at all.

  read-through pattern always fires the GraphQL request in the background — even
  when you have fresh cached data one second old. So every page visit = a
  GraphQL call, even though the cached image URLs are already good.

  The fix: add a freshness window (TTL). If the cached entry is younger than the
  TTL, serve it and skip the network entirely — zero GraphQL calls, images
  render straight from the cached URLs. Only revalidate when the cache is
  missing or stale.

  How it works now

  - app/dashboard/products/page.tsx holds currentPage state, requests pageSize: 
  24 per page, and renders Previous/Next buttons (lines 454–475).
  - Each page fetch replaces the grid: setProducts(res.items) (line 105).
  - The catalog is large — your screenshot showed Total: 7673 products (~320
  pages at 24/page).
  - Cache is keyed per page (storefront:{...currentPage:N...}), so each page is
  cached separately in IndexedDB.

  Options to remove pagination

  1. Infinite scroll — recommended. Keep server paging under the hood, but
  instead of Prev/Next, auto-load the next page when the user scrolls near the
  bottom, and append instead of replace:
  - Change setProducts(res.items) → setProducts(prev => [...prev, 
  ...res.items]).
  - Add an IntersectionObserver sentinel at the grid bottom that does
  setCurrentPage(p => p+1) while currentPage < totalPages and not already
  loading.
  - On search/brand/filter change, reset the list and go back to page 1
  (otherwise old results mix in).
  - ✅ Works with the existing per-page cache + TTL, requests stay small (24 at
  a time).

  2. "Load More" button. Same append mechanic, but a manual button instead of
  the scroll observer. Simplest and fewest edge cases.

  3. Fetch everything in one query (pageSize: 7673). One call, no paging — but
  I'd advise against it:
  - Magento GraphQL usually caps pageSize (commonly ~300). A giant value likely
  errors or silently truncates — we'd need to confirm your store's limit first.
  - ~7673 product cards each with a next/image render will make the browser
  janky without virtualization.
  - Large single payload = slow first paint, heavy memory.

  4. Fetch all + virtualize (react-window / react-virtual). True "show all" with
  good scroll performance, but the heaviest change and still depends on the
  store's pageSize cap.

  My recommendation

  Go with infinite scroll (or Load More if you want it dead simple). Both remove
  the Prev/Next bar, keep each request light, and reuse your current cache/TTL
  logic unchanged — no giant query, no virtualization needed.
